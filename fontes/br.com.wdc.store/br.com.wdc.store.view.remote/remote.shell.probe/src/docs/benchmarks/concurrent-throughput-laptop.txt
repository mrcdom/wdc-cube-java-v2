══════════════════════════════════════════════════════════════════════
  RESULTS ANALYSIS
══════════════════════════════════════════════════════════════════════

  Test topology
  ─────────────
  Backend       : laptop (M4 Max, 16 cores — 12P + 4E)
  PostgreSQL    : remote server (2x Xeon, Docker), local network (LAN)
  Client        : laptop (same process/machine as the backend)

  Degradation curve — the laptop CPU is the bottleneck
  ────────────────────────────────────────────────────
    100 sessions →  23,197 req/s   p50 =  5 ms
    200 sessions →  18,287 req/s   p50 = 10 ms
    500 sessions →  11,953 req/s   p50 = 50 ms
    800 sessions →   9,234 req/s   p50 = 100 ms

  With server and client on the same laptop, the two processes compete
  for the 16 cores. Little's Law confirms the CPU saturation:

    500 sessions / 11,953 req/s ≈ 42 ms mean latency  ✓ (p50 = 50 ms)
    800 sessions /  9,234 req/s ≈ 87 ms mean latency  ✓ (p50 = 100 ms)

  Comparison with a local PostgreSQL run
  ──────────────────────────────────────
  In the local run PostgreSQL ran on the laptop itself. With the database
  on the remote server, the laptop CPU is fully dedicated to
  backend + client:

    500 sessions, local PG  →  7,455 req/s   (PostgreSQL competed for the 16 cores)
    500 sessions, remote PG → 11,953 req/s   (+60%)

  This shows that a local PostgreSQL took ~37% of the laptop's CPU
  capacity under the test conditions.

  Effect of the remote PostgreSQL on base latency
  ───────────────────────────────────────────────
  Each request's latency includes 1–2 SQL queries to PostgreSQL
  over the LAN. The impact shows in the distribution at 100 sessions:

    100 sessions, local PG  →  60.7% ≤5 ms,  39.0% 5–10 ms
    100 sessions, remote PG →  60.7% ≤5 ms,  39.0% 5–10 ms  (identical)

  The LAN adds ~1 ms per query, but since virtual threads wait on I/O
  without blocking carrier threads, that overhead is absorbed with no
  throughput degradation at moderate loads.

  Sweet spot for this hardware
  ────────────────────────────
  At 100–200 sessions the laptop delivers 18,000–23,000 req/s with p50 ≤ 10 ms.
  Above 200 sessions throughput drops in proportion to the increase in
  sessions — CPU saturation from backend + client sharing the machine.

  To scale beyond 200 sessions on this hardware, the test client
  must run on a separate machine.

  Heap
  ────
  The heap shrinks as sessions grow (4.83 → 2.41 GB from 100 → 800):
  more sessions → slower requests → fewer objects created per
  second → ZGC keeps a smaller heap. Pattern consistent with Generational ZGC.
