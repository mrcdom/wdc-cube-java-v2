══════════════════════════════════════════════════════════════════════
  RESULTS ANALYSIS
══════════════════════════════════════════════════════════════════════

  Test topology
  ─────────────
  Backend       : server (2x Xeon Platinum 8368, 152 vCPUs, 1.5 TiB)
  PostgreSQL    : Docker container on the server itself (local access)
  Client        : same server (local ConcurrentThroughputScenario)

  The bottleneck is per-request processing speed on the Xeon
  ────────────────────────────────────────────────────────────────────
  Throughput stays almost constant between 100 and 800 sessions:

    100 sessions →  6,878 req/s   (p50 = 20 ms)
    500 sessions →  7,169 req/s   (p50 = 100 ms)
    800 sessions →  7,397 req/s   (p50 = 100 ms)

  The same PostgreSQL (same Docker container, same host) served
  the laptop with p50 = 5 ms and 23,197 req/s at 100 sessions — 3×
  faster, even reaching the database over the network. If the database
  were the bottleneck, the server with local access would be faster,
  not slower. PostgreSQL is not the bottleneck.

  Little's Law shows that the ceiling is the per-request latency:

    throughput ≈ sessions / mean_latency

    server: 100 / 0.0145 s ≈  6,900 req/s  ✓  (p50 = 20 ms)
    laptop: 100 / 0.005  s ≈ 20,000 req/s  ✓  (p50 =  5 ms)

  The difference lies in the per-request processing speed of the
  Javalin + jOOQ + JSON pipeline on each hardware:

  - M4 Max (~4+ GHz effective, Apple Silicon):
    ~5 ms per request → 20,000 req/s possible at 100 sessions
  - Xeon Platinum 8368 (2.4 GHz base, optimized for parallel
    throughput, not single-thread):
    ~20 ms per request → ~5,000–7,000 req/s at 100 sessions

  With fire-and-wait each virtual thread processes one request at
  a time. Throughput depends on per-request speed, not on the core
  count. With 100 sessions and 152 vCPUs there is no CPU
  contention — the Xeon simply processes more slowly.

  Latency distribution at 100 sessions
  ────────────────────────────────────
  The cluster at 10–20 ms (46.9% of requests) is the signature of
  the processing time on the Xeon. The 13.9% at ≤ 5 ms are requests
  that hit a warm cache (JIT-compiled code, data in the PostgreSQL
  cache) and completed in the pipeline's minimum time.

  Heap
  ────
  The heap stays low (1.4–2.4 GB) even with 800 sessions, because
  PostgreSQL runs in a separate process and does not use JVM heap.
  With 1.5 TiB of RAM available, memory is not a constraint on this server.

  Real server capacity
  ────────────────────
  The Xeon has 152 vCPUs — huge parallel capacity. To exercise it,
  the scenario needs enough concurrency to saturate parallel
  processing. With fire-and-wait at 100–800 sessions, each core
  processes sequentially; the gain comes from running more
  simultaneous sessions. The practical ceiling is when all 152 vCPUs
  are busy — estimated at tens of thousands of concurrent sessions
  with a real distributed load.
